02 · Product decisions and defaults

Start with the instructor’s approved main questions. Students answer them in a confirmed order, receive an approved explanation after each submission, and collect mistakes for review after the main sequence. Review follows a finite, published set of rules and prepared content. Student requests never initiate AI generation.

DecisionRecommended defaultBoundary
Main sequenceTopic → LO → instructor-confirmed orderOrdering is plan metadata, not an edit to question content
DiagnosisWrong options indicate possible misconceptions; diagnostic questions add evidenceOne incorrect answer is not a certain diagnosis
Content reviewReview main, diagnostic, guided and transfer questions individuallyNew content never inherits approval from its source question
Parameter reviewApprove a template, constraints and an exact, finite set of validated instancesNew wording or structure requires separate content review; this approval policy needs design confirmation
Review budgetAt most 3 answers per skill and 6 per session; allow finishing or returning laterThe prototype demonstrates one skill with at most 3 answers
Initial scopeFinance MCQ, T/F and numerical questions supported by the closed formula evaluatorOpen-ended AI scoring is outside the no-runtime-AI scope
PublicationOpt in by course and Topic; apply a revision to new sessionsDo not silently change ongoing sessions
Missing supportKeep the original explanation, review reminder and approved resourcesShow the gap rather than substituting an unrelated question

A coverage contract instead of unlimited branching

For each skill, define the evidence required: a main question; diagnosis and support for important misconceptions; parameter practice for a stable numerical structure; optional transfer or delayed checks. Identify reusable approved content before generating missing pieces. Display reused, new, excluded and missing outputs with a bounded budget. Do not try to enumerate every possible student error.

05 · Knowledge graph and teaching model

Four distinct layers

  1. Curriculum: Topic → LO → assessable skill. Skills use specific action statements, such as “discount a year-n cash flow to today.” Prerequisite relations must form a DAG.
  2. Diagnosis: a version-specific option or error rule → possible misconception → diagnostic evidence → appropriate support. Store whether a relation is instructor-authored, rule-derived or AI-proposed.
  3. Content: main questions, diagnostics, guided practice, parameter packs, contextual transfer and resources. Families preserve lineage without asserting equivalent difficulty or purpose.
  4. Learner evidence: first pass, skip, hint exposure, diagnosis, supported response, independent check and delayed check. Record exact versions and routing reasons.
Skill S02: discount-cash-flow-to-present
  prerequisite → S00: read-cash-flow-timeline
  assessedBy   → Q043 / version 3
  suspectedBy  ← M02: one-period-discounting
  diagnosedBy  → D01 / version 1
  remediatedBy → R01 / version 1
  verifiedBy   → F043 / template 1 / deployed instance set

Every relation carries course scope, stable IDs, revision, origin,
source evidence, review state, reviewer and review timestamp.

Content graph and student route are different objects. A shared skill can connect multiple main questions to the same reviewed support. The main sequence is an ordered list. A review session traverses published relations using a bounded state machine; it does not copy an entire tree for each main question.

Two version boundaries: graph/plan revisions pin relationships and order; question/template versions pin actual content. Changing a relation does not rewrite the source question. Editing a question does not replace it in existing sessions.

RAG remains the evidence layer

Use retrieval to ground proposals and generation in source material. Store confirmed skills and typed relations independently in MongoDB; retain Qdrant for evidence retrieval. Node/edge collections with indexes are sufficient initially. Adopt a graph database only if measured traversal requirements justify it. AI confidence is a review signal, not a calibrated probability of correctness.

06 · Complete teacher and student journeys

Instructor: extend existing approved questions

  1. Select a Topic and approved versions. Display provenance, parameter capabilities and the existing main order.
  2. Click Analyze. Capture a read-only version snapshot; propose skills, important misconceptions, reuse candidates and gaps. Show source excerpts and uncertain relationships.
  3. Confirm the scope. Distinguish reused questions, new content, parameter instances and accepted fallbacks. Show actual budget limits without invented price estimates.
  4. Start generation explicitly. Surface queued, generating, validating, quality review, saved and pending-review states per output. Preserve completed drafts if one branch fails.
  5. Review new semantic content individually. Review a parameter pack as template + constraints + exact deployed instance set. Changed content requires a fresh approval.
  6. Exercise the real Student Preview adapter with correct, incorrect, unavailable-content, budget and resume scenarios.
  7. Review publication checks and revision differences, then publish. Only new sessions adopt the new plan.

Instructor: start a new course from LOs

Propose a skill map and coverage contract from materials and LOs, confirm main-question and support budgets, and use the same review and publication flow. The existing Create a batch workflow stays available. Its outputs can join a learning sequence after approval.

Student: main sequence, then focused review

  1. Start a server-persisted session with pinned plan, order and instances.
  2. Answer the main questions in order. Show approved feedback and queue mistakes. A skip is recorded separately and does not count as a wrong or correct answer.
  3. Show a stable main-sequence summary. Support questions do not increase the main denominator.
  4. Deduplicate review by skill and apply a stable priority policy. Unknown misconceptions fall back to skill-level support.
  5. Diagnostic correct → independent new-number check. Diagnostic incorrect → prepared explanation and guided practice → new-number check.
  6. Stop at the skill or session budget. If the check is still incorrect, preserve the review item and show resources or a help route. Do not recursively generate more questions.
  7. Resume persisted progress after navigation. Re-practice creates a new exposure and preserves the first attempt; Review Book returns to the exact original version.
No-runtime-AI applies to prepared closed-answer content, feedback and routing. Grading, eligibility and next-step decisions still run on the server. Never download correct answers or unseen branches to the student client before they are needed.

Teaching invariants matter

For multi-period discounting, n = 1 makes the “discount once” distractor identical to the correct answer and removes the target skill. Validate n ≥ 2, positive rates, ranges, units, cash-flow timing, rounded choice uniqueness and difficulty boundaries. Random sampling does not prove an infinite parameter space safe. The initial release serves a finite set of fully validated instances.

Partial failure and recovery

Runs follow queued → running → completed / failed / cancelled; outputs independently track pending, generated, invalid and review-ready states. Retries under the same snapshot generate only missing outputs. A new source or teaching intent creates a new revision. CAS, unique output keys and idempotent persistence prevent duplicate questions. SSE sequence recovery restores progress. Interrupted workers become explicitly retryable rather than remaining indefinitely “processing.”

Consistency and runtime separation

Persist the complete immutable manifest before atomically switching the active pointer. Use idempotency and session revision checks to prevent double-click or multi-tab duplicate successors. Use Mongo transactions only if deployment supports them; otherwise use a durable commit/outbox and idempotent projections with recovery. Student Preview shares the pure routing engine but retains Instructor-only entry and separate storage. Tests should assert zero LLM calls on the new student path.

Rollout

  1. Deploy compatible optional schemas and read paths with course opt-in off by default. Old generation runs finish with their original snapshots.
  2. Run read-only course inventories of versions, parameter support, sources and gaps.
  3. Let instructors explicitly build draft metadata and new content. Existing student routes remain available.
  4. Validate in an isolated test course and Student Preview before enabling real students.
  5. Publish one Topic revision and use it only for new sessions. Do not require the whole course to be complete.
  6. Monitor missing content, serving failures, review abandonment and question flags before expanding.

Version approval is not permanent serving permission

Legacy Approved is often the current question state. Do not assume every historical version was approved. Capture evidence for the specific approved version admitted to a plan. Normal edits create a new draft revision; they do not replace active-session content. Paused, archived or revoked content can still block serving from an old manifest, with an explicit explanation and approved replacement or safe skip.

Routine rollback changes the default for new sessions. It preserves existing sessions, attempts and audit records. Emergency withdrawal targets unsafe content. New collections, projections, Preview TTL records and Agenda jobs must join the existing course-deletion and retention lifecycle. A software rollback must tolerate already-written additive schemas.
